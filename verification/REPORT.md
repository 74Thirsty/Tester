# Google / Microsoft account management — implementation and evidence

## Outcome and scope

The application now has separate Google/Gmail and Microsoft/Outlook website adapters, isolated persistent browser workers, shared encrypted account metadata, direct CLI/menu selection, user-completed signup/sign-in checkpoints, identity observations, sign-out confirmation, and local removal. Useful earlier vault/generation/clipboard repairs are preserved; their earlier report is [archived here](LEGACY_VAULT_REPORT.md).

**Authenticated Google and Microsoft acceptance is not complete.** No controlled test-account credentials were supplied or entered. No external account was created, terms accepted, CAPTCHA bypassed, email sent, API authorization granted, or paid service provisioned. Real-browser **local fixtures** are automation evidence, not real-provider authentication evidence. Anonymous provider navigation is reported separately below.

Final automated result: **48 tests passed in 28.180 seconds** in the clean environment. Both real-browser fixture scripts passed, including a real connection drop/recovery through the worker, persistent storage isolation, trusted-frame sign-out and full CLI/menu dispatch. Dependency checks, compilation and diff whitespace checks also passed. [Test output](platform-tests.log), [worker output](worker-browser.log), [browser output](session-browser.log), and [source snapshot](source-manifest.json) are retained.

Inspected configuration: project `.env` and `.env.local` absent; no `TESTER_*`, `GOOGLE_*`, `MICROSOFT_*`, or `AZURE_*` environment configuration was present when inspected. An existing encrypted default vault exists, but its contents were not decrypted or modified. Connected email APIs were not treated as browser sessions or authorization to use personal accounts as test accounts.

## Implementation

- [tester_platforms.py](../tester_platforms.py): provider public entry points, strict origin and account-chrome identity observations, mail UI checks, visible authentication checkpoints, sign-out controls including trusted provider frames. Unknown layouts and ambiguous identities do not pass. English UI is targeted.
- [tester_sessions.py](../tester_sessions.py): one random persistent profile per account, private file IPC and browser pipe, per-profile locks, restart reuse, bounded navigation, checkpoint preservation, sanitized errors, closing and local cleanup. No exported cookies, remote debugging listener, automated password entry or secret continuation URLs.
- [tester.py](../tester.py): shared CLI/TUI account lifecycle, single-number menu switching, encrypted observations with timestamps, durable signup intents, identifier correction, save-failure recovery and explicit partial-effect errors. Standalone commands unlock the vault; the TUI unlocks once.
- [pyproject.toml](../pyproject.toml): declares Playwright and packages all three modules. [README](../README.md) documents install, commands, browser requirements, semantics and limitations.

Website authentication, authenticated mail UI, account creation, and API authorization are distinct. An account email in a message is never identity proof. The app observes only account UI plus a mail main region, at an allowed HTTPS origin. A fresh navigation observation is not an OAuth token grant or a claim about every subsequent server request. Cached list status is explicitly labeled with the last observation and last fresh-navigation state/time. Provider-side expiry/revocation requires a new navigation to observe.

## Reproduction and evidence boundaries

```sh
python3 -m venv /tmp/tester-platform-clean
/tmp/tester-platform-clean/bin/python -m pip install -e '.[dev]'
TESTER_EVIDENCE_DIR=verification /tmp/tester-platform-clean/bin/python -m unittest discover -s tests -v
/tmp/tester-platform-clean/bin/python -m pip check
/tmp/tester-platform-clean/bin/python verification/check_sessions.py
/tmp/tester-platform-clean/bin/python verification/check_worker_workflows.py
/tmp/tester-platform-clean/bin/python verification/probe_provider_portals.py
```

Browser scripts require a graphical desktop and Chromium with sandbox support. They use dedicated temporary profiles, no personal browser profile, and no production vault. The fixture server is HTTP on loopback with fake identities and fake cookies; production adapters allow only their configured HTTPS origins. Fixture adapters are substituted only inside test processes, not exposed as a production “accept any provider” configuration.

`worker-browser.log` records entry-point paths, exact command arguments, non-secret menu inputs, exits, assertions and selected observation states. Inputs contain synthetic identifiers only; vault passwords are omitted. The log's short observation list is not a full menu transcript; the script also asserts result text and persisted state. `session-browser.log` covers real-browser storage and restart checks, including sign-out controls in a trusted frame. `provider-portals.json` contains only static checkpoint messages/state and timings, no redirected URLs or page contents. Earlier raw browser/clipboard failure evidence uses synthetic fixtures only.

The live acceptance runner is prepared, compiled and help-checked, but **not run against controlled accounts**. It writes only labels A/B, statuses and measurements. It never records account emails, passwords, tokens, cookies, authentication URLs, message contents or screenshots. Its signup mode requires the user to attest that creation was actually completed, plus a fresh matching identity/mail observation; it does not mislabel existing-account sign-in as proven new creation.

## Performance interpretation

Timings distinguish account lookup, browser activation, navigation/observation, startup/IPC/scheduling and encrypted vault save. CLI samples include interpreter startup and synthetic vault unlock/save. TUI reuse avoids repeatedly unlocking the vault; it does not suppress provider MFA. Browser process/profile reuse avoids repeated launch/setup. Fresh mail navigation is deliberately retained so expired sessions are not represented as freshly authenticated based only on a cached list or stale page.

Local conditions: Linux, Python 3.11, headful Chromium, two isolated profiles per adapter, loopback synthetic provider, sequential benchmark samples. Two cold/initial samples per adapter precede eight alternating warm samples. There is no real provider latency or human authentication in these measurements. Values are populated from the retained JSON below; “rapid” is not claimed for real Gmail/Outlook without live samples.

| Measurement | Adapter shape | Samples | Median | Slowest |
|---|---|---:|---:|---:|
| Complete CLI warm switch | google | 8 | 433.60 ms | 492.68 ms |
| Initial worker CLI (startup may already be underway) | google | 2 | 835.43 ms | 844.72 ms |
| Browser operation only, warm | google | 8 | 95.88 ms | 101.13 ms |
| Initial browser launch + fixture sign-in | google | 2 | 495.35 ms | 502.92 ms |
| Complete CLI warm switch | microsoft | 8 | 459.40 ms | 486.05 ms |
| Initial worker CLI (startup may already be underway) | microsoft | 2 | 842.01 ms | 847.29 ms |
| Browser operation only, warm | microsoft | 8 | 107.37 ms | 118.42 ms |
| Initial browser launch + fixture sign-in | microsoft | 2 | 477.10 ms | 484.61 ms |

`activation_ms` is browser-side activation, not a user-visible guarantee that a window manager raised it. `navigation_and_observation_ms` includes browser loading/rendering plus network work; those cannot be separated precisely by DOM timing alone. `startup_ipc_and_scheduling_ms` is measured residual client overhead, not pure CPU time. Manual authentication is outside switch timers; provider sign-in checkpoint latency is available in the anonymous probe but is not time to authenticated mail. The live runner measures initial operation samples and repeated switching and marks unavailable checkpoints blocked.
